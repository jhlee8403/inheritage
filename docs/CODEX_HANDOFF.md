# Codex 전달문 — 상속인·법정상속분 계산 도구

작성일: 2026-10-18  
문서 버전: handoff-v0.3  
작업 대상: `jhlee8403/inheritage`  
이번 작업 범위: 원본 첨부자료 검토, 설계·검증 계획 작성, 문서 전용 커밋  
승인 상태: 제품 방향 합의 / 개별 법률 규칙·정답 후보 승인 대기

이 문서는 사용자가 원본 두 자료를 Codex 작업에 직접 첨부한다는 전제의 전달문이다. 이 파일이 저장소에 있다는 사실은 Codex 실행 환경의 준비, 실제 모델 설정, 법률 승인, OCR 시험 완료를 의미하지 않는다.

v0.3 변경: 모호한 ‘선택된 저장소’를 실제 저장소 주소로 특정하고, 실행 환경 미준비와 저장소 접근 실패를 구분하는 절차를 추가했다. 원자료의 법률 내용을 바꾸거나 새 법률 결론을 추가하지 않았다. 기존의 설계 전용 범위는 유지한다.

## 0. 작업 대상과 실행 환경을 먼저 확인하라

### 0.1 정확한 작업 대상

- 저장소: **`jhlee8403/inheritage`**
- 웹 주소: **https://github.com/jhlee8403/inheritage**
- HTTPS Git 주소: **https://github.com/jhlee8403/inheritage.git**
- 확인된 기본 브랜치: **`main`**. 실제 작업 시 메타데이터를 다시 확인한다.
- 전달문 경로: **`docs/CODEX_HANDOFF.md`**
- 후속 설계 문서 경로: **`docs/inheritance/`**

이름을 `inheritance`로 고치거나 다른 저장소로 대체하지 말라. `jhlee8403/-`, `jhlee8403/demo`, PDF.js·Tesseract.js 등의 참고용 공개 저장소는 작업 대상이 아니다. 새 GitHub 저장소를 임의로 만들지 말라.

작성 시 이 저장소는 공개 상태로 확인되었다. 공개 여부와 무관하게 원본 주석서, 실제 사건자료, 개인정보, 인증정보를 커밋하지 않는다. 사용자가 요청한 자체 작성 전달문과 설계 문서만 보존한다.

### 0.2 실행 환경과 저장소 지정은 별개다

위 URL을 프롬프트에 적었다고 Codex 환경에 저장소가 연결되거나 실행 권한이 생기는 것은 아니다. 현재 작업 환경에 이 저장소가 포함되어 있는지 확인하라.

터미널을 사용할 수 있으면 실제 작업 경로, `git rev-parse --show-toplevel`, `git status --short`, 현재 브랜치와 원격 저장소 식별자를 확인한다. 원격 주소에 인증정보가 들어 있으면 보고에서 반드시 가린다. HTTPS·SSH 등 주소 형식이 달라도 실제 소유자/저장소가 `jhlee8403/inheritage`인지 비교한다.

기존 `AGENTS.md`, README, 기여 규칙과 다른 사람의 변경을 먼저 확인한다. 작업 경로와 접근한 저장소를 확인하지 못한 상태에서 파일 작성·커밋을 수행하지 않는다.

### 0.3 환경이 pending / offline인 경우

- 환경 상태 조회가 성공했다는 사실과 실행 환경이 준비되었다는 사실을 구분한다.
- 실행 명령을 사용할 수 없으면 실행했다고 주장하지 않는다.
- 확인된 상태, 오류 코드, 마지막 준비 단계, 사유 제공 여부를 한 번 정리해 보고한다. 같은 상태를 무한 반복 조회하거나 ‘준비되면 나중에 하겠다’는 말만 반복하지 않는다.
- `failure: null` 등은 사유가 제공되지 않았다는 뜻으로 보고하고 특정 원인으로 단정하지 않는다.
- 첨부자료를 별도로 읽을 수 있다면 읽은 범위의 설계 초안은 작성할 수 있다. 읽지 못한 자료를 읽었다고 하거나, 저장소 저장·커밋까지 완료했다고 보고하지 않는다.
- 상태 확인과 자료 검토가 불가능하면 그 제약과 사용자가 확인할 환경·저장소 항목을 보고하고 해당 시도를 종료한다. 새 저장소 생성, 인증정보 요구, 보안 정책 우회로 해결하지 않는다.

**‘완성 앱의 오프라인 실행’은 개발용 Codex 환경의 시작·저장소 연결을 금지한다는 뜻이 아니다.** 개발 환경의 네트워크·권한 설정은 기존 승인 범위 안에서 사용하고 임의로 확대하지 않는다. 환경의 `pending`과 아래 법률 규칙의 `PENDING`은 서로 다른 상태다.

## 1. 역할과 이번 작업의 경계

대한민국 민사사건에서 사용할 상속인·법정상속분 계산 도구를 설계한다. 확인된 가족관계에 따라 최초 피상속인의 지분이 대습·연속상속을 거쳐 누구에게 얼마씩 귀속되는지, 그 경로와 근거를 검토할 수 있게 하는 것이 목표다.

**이번 첫 작업은 단계 A: 원자료 검토와 설계·검증 계획 작성이다.**

허용: 자료 읽기, 저장소 상태 확인, 자체 작성 설계 문서의 생성·검토, 문서 전용 브랜치·커밋 및 허용된 원격 반영.

금지: 계산 엔진·UI·PDF 처리·OCR 실행 코드 작성, 개발 의존성 설치, OCR 모델 다운로드, 앱 빌드·배포, 런타임·네트워크·보안 설정 변경. 큰 실행 코드를 ‘설계 예시’라고 부르며 작성하지 않는다.

‘설계만’은 제품 구현을 금지한다는 뜻이지, 문서 파일 생성과 Git 커밋까지 금지하는 읽기 전용 클라이언트 모드를 강제한다는 뜻이 아니다.

설계 가능한 부분은 먼저 작성하고, 소유자 결정이 필요한 부분은 안전한 잠정 처리와 결정권자를 기록하라. 미확정 사항 때문에 질문 목록만 반환하지 말고, 확인 없이는 위험해지는 해당 부분만 보류한다. 단계 B 이후는 별도 승인 없이 시작하지 않는다.

## 2. 실행 모델과 노력 정도

### 2.1 권장값

| 작업 | 권장 모델 | 노력 정도 / 추론 강도 |
|---|---|---|
| 이번 원자료 검토, 데이터·엔진 설계, 검증 체계 수립 | GPT-6 Astra (`gpt-6-astra`) | Extra High (`xhigh`) |
| 핵심 계산 로직 별도 검토·난해한 오류 분석 | GPT-6 Astra (`gpt-6-astra`) | Extra High (`xhigh`) |
| 승인 후 일반 구현·PDF·OCR·저장 기능 통합 | GPT-6.1 Sol (`gpt-6.1-sol`) | High (`high`) |
| 단순 문구·문서·배치 수정 | GPT-6.1 Sol (`gpt-6.1-sol`) | Medium (`medium`) |

이는 프로젝트 운영상 권장값이며 정확성을 보증하거나 법률 검증을 대신하지 않는다. 모델의 존재와 일반 제공 안내는 OpenAI 공식 발표 [M1–M2], 추론 설정은 공식 설정 문서 [M3]를 참고한다. 실제 계정·워크스페이스·클라이언트에서 모델과 추론 단계의 선택 가능 여부는 별도로 확인한다. `xhigh` 지원은 모델·클라이언트에 따라 달라질 수 있다.

### 2.2 실제 설정

사용자는 작업 시작 전에 Codex의 모델 선택 화면 또는 지원되는 클라이언트 설정에서 값을 선택한다. 자연어 전달문만으로 실제 실행 모델이나 추론 강도를 변경했다고 주장하지 말라.

확인 가능한 설정·메타데이터만 기록하고 확인할 수 없으면 `실제 모델 미확인` 또는 `실제 추론 강도 미확인`으로 남긴다. 확인하지 못했다는 이유만으로 읽을 수 있는 자료의 설계를 중단하지 않는다.

지원되는 CLI/IDE에서 확인할 설정 예시이며, 이번 작업에서 설정 파일을 생성·변경하라는 지시는 아니다.

```toml
model = "gpt-6-astra"
model_reasoning_effort = "xhigh"
```

Astra 또는 xhigh가 제공되지 않으면 실제 선택 가능한 모델·강도를 확인하고 GPT-6.1 Sol + High를 대안으로 제시한다. 임의의 모델 ID를 만들어 쓰지 않는다. 웹 작업에 로컬 설정 파일이 자동 적용된다고 설명하지 않는다.

실행 기록에는 권장값과 실제값, 클라이언트, 참조 문서 버전, 작업 범위, 커밋과 수행한 검증을 구분해 남긴다. 높은 추론 강도는 추가 권한이나 다음 단계 실행 허가가 아니다.

**개발용 모델을 완성 앱의 실행 의존성으로 넣지 않는다.** 업무 PC의 OCR 모델은 별도 선정하며, 상속 계산은 확인된 사실관계와 승인된 규칙에 따른 재현 가능한 코드로 수행한다.

- 실제 파일명은 한글 유니코드 정규화나 접두사 표기가 다를 수 있다. 첨부 목록과 문서 제목으로 확인하며 임의 경로를 읽었다고 주장하지 않는다.

필수 두 자료 중 읽지 못한 자료나 범위가 있으면 명시한다. 법률 발췌에 없는 조문·판례·해석을 그 자료의 설명인 것처럼 쓰지 않는다. 저장소에 원자료가 없다고 존재하지 않는 파일을 전제로 하지 말고, 작업에 첨부된 자료의 접근 여부를 확인한다.

### 3.2 보조 기획자료

`INHERITANCE_CODEX_BRIEF_v0.1.md` 또는 `inheritance_planning_v0_1.zip`이 함께 제공되면 보조 기획자료로 대조한다. 통합본의 `SPEC.md`, `RULES.md`, `TEST_CASES.md`, `SOURCES.md`, `VALIDATION.md` 등은 해당 절을 뜻한다.

`NUMERIC_CASES.json`이 있으면 정답 후보 참조 데이터로 검토하되, 실행 가능한 테스트나 법률적으로 승인된 정답으로 간주하지 않는다. 보조 패키지는 필수가 아니다. 없으면 존재하지 않는 규칙 ID·시험 수·검산 결과를 만들지 않는다.

### 3.3 근거 표시

- `원자료`: U1·U2가 실제로 설명한 내용. 제목·조문·절·쪽수 또는 파일 위치를 연결한다.
- `소유자 합의`: 이 전달문에 정리한 제품 요구와 개발 범위.
- `설계 제안`: 새 데이터 구조·구현 방식·성능 목표.
- `외부 확인`: 추가 확인한 공식 문서·법령·판례. URL, 확인일, 해당 부분을 기록한다.
- `미확인/승인 대기`: 자료 누락, 해석 충돌, 검증 미실시, 사용자 결정 필요.

원자료의 용어·쟁점 구분·설명 순서를 보존하고, 구현 목적의 재구성은 대응표로 표시한다. 원문의 ‘학습시킨다’는 구상을 아래 규칙 엔진 설계가 원래 원문이었던 것처럼 바꾸지 않는다.

최신 외부 자료와 원문이 충돌하면 `원자료 설명 / 외부 확인 / 영향 / 승인 상태`로 비교한다. 원문을 조용히 수정하거나 일반 지식으로 빈틈을 메우지 않는다.

**주석서 전체·원본 첨부자료를 이 저장소에 복제하지 않는다.** 첨부는 읽기 위한 것이며 공개 복제 허가가 아니다. 자체 작성 요약·규칙 초안과 최소한의 출처 표시만 커밋한다.

## 4. 확정 요구와 미정 사항

### 4.1 실행·입력·출력

- 인터넷 없는 업무 PC의 **Microsoft Edge에서 로컬 실행**한다.
- 텍스트 PDF, 스캔 이미지 PDF, 페이지·영역별 혼합 PDF를 지원한다.
- **오프라인 OCR은 필수**다. 첫 실행부터 온라인 다운로드 없이 작동해야 한다.
- 결과는 선택·복사할 수 있는 일반 텍스트다. PDF 보고서와 엑셀 출력은 필수가 아니다.
- 자동 복사 실패 시 직접 선택·키보드 복사를 제공한다.
- 명시적 로컬 저장·불러오기로 작업을 재개한다. 사건자료의 자동 영구저장은 기본으로 하지 않는다.

### 4.2 계산 범위

법정상속인·법정상속분·대습상속·연속상속이 핵심이며, **1960년 이후 과거법**을 지원 대상으로 설계한다. 현재법만의 단순 계산기로 대체하지 않는다.

1960년 이전 구관습법과 복잡한 예외는 별도 지원 범위로 표시한다. 지원하지 않는 과거 단계가 최종 지분에 영향을 주면 그 단계와 후속 결과를 보류한다. 검토자가 외부 판단으로 확정한 중간 지분을 제공하면 근거와 전제를 표시해 이후 계산을 이어가는 방안을 설계할 수 있다.

특별수익·기여분·유류분·상속세·협의분할·유증·처분의 효력, 실제 채무 변제책임, 소송수계·송달 적법성은 1차 자동 판단에서 제외한다. 관련 사정은 무시하지 말고 ‘법정상속분 기초계산’과 ‘실제 권리귀속 확정’을 구분한다.

### 4.3 아직 확정하지 않은 것

업무 PC의 OS·사양·Edge 버전·관리 정책, 별도 실행기·로컬 서버 허용 여부, OCR 엔진·모델, 단일 HTML 여부, 문서 유형별 정확도·성능 목표, 법률 승인자, 저장 파일 암호화·원본 동봉 범위는 미정이다. 확정된 사실처럼 문서화하지 않는다.

### 4.4 개인정보

개발·시험에는 처음부터 만든 가공 자료를 사용한다. 실제 사건자료를 가명 처리했다는 이유로 개발 AI·GitHub·공개 OCR 데모에 전송하지 않는다.

실제 PDF, OCR 원문, 주민등록번호, 계정·토큰·비공개 접근정보를 Git·Issue·PR·원격 로그에 넣지 않는다. 완성 앱에는 외부 OCR·온라인 AI·분석·오류수집·인증·CDN 등 필수 외부 의존성을 두지 않는다.

주민등록번호 전체를 필수 인물 ID로 삼지 않고, 복사 출력에서는 불필요한 식별정보를 기본적으로 제외한다. 저장 파일에 포함되는 정보와 보안 선택을 사용자에게 드러낸다.

## 5. 사실관계 확인과 계산 엔진을 분리하라

```text
PDF 입력
→ 직접 텍스트 추출 / 필요한 페이지·영역의 로컬 OCR
→ 인물·날짜·관계 후보 구성
→ 사용자의 원문 대조·확정
→ 상속 사건별 규칙 선택
→ 정확한 분수 연산
→ 단계별 경로·근거·경고·최종 지분 표시
```

OCR 성공은 가족관계나 법률 효력의 확정이 아니다. 생성형 AI의 런타임 답변을 계산 정답으로 쓰지 않는다. 로컬 생성형 모델은 1차 필수가 아니며 별도 제안·검증 대상으로 둔다.

### 5.1 데이터 모델

| 객체 | 표현할 내용 |
|---|---|
| 사건 | 내부 ID, 최초 피상속인, 시작 지분, 결과 기준일, 입력 데이터 버전 |
| 인물 | 고유 내부 ID, 원문 성명·별칭, 필요한 역사적 속성, 검토 상태 |
| 관계 | 친생·일반입양·친양자·혼인 등 유형, 효력 기간, 근거 |
| 일자 | 원문, 해석값, 사망일·신고일·발급일 등 종류, 정밀도·가능 범위, 연호·달력 |
| 상속 사건별 상태 | 대상 피상속인·상속 사건·인물·필요시 자격 경로, 포기·한정승인·결격·상실의 원인·근거 |
| 자료·검토 | 문서 ID, 파일 식별정보, 페이지·좌표, 추출 방식, 사용자 확인·수정 이력 |
| 규칙 | 적용 조건, 효력 시점·경과규정, 출처, 버전, 승인자·승인 상태 |
| 결과 | 기약분수, 취득 경로, 적용 규칙, 제외 사유, 미해결 지분, 가정·검토 상태 |

‘상속포기자’를 사람의 전역 속성 하나로 저장하지 말고 각 상속 사건에 연결한다. 인물 ID와 자격 경로를 구분하되, 복수 자격의 법률 효과를 자동 합산하지 않는다.

이름이 같다고 자동 병합하지 않는다. 병합 후보, 사용자 확인, 분리·되돌리기를 설계한다. 현재 가족관계를 모든 과거 사망 시점에 적용하지 않는다. 단순 가계도 표시와 관계·시간을 표현하는 내부 모델을 구분한다.

### 5.2 미확인 값

`있음 / 없음 확인 / 미확인`을 구분한다. 배우자·자녀가 문서에 보이지 않는다는 이유로 없다고 처리하지 않는다. 사망일을 신고일·발급일로 대신하지 않고, 연도만 있는 날짜에 임의 월일을 넣지 않는다. 같은 날짜의 사망을 자동으로 동시사망으로 취급하지 않는다.

핵심 사실이 미확인이면 계산 보류 또는 전제가 명확한 잠정 계산으로 표시한다. 입력·관계·규칙을 바꾸면 기존 결과는 즉시 재계산 필요 상태로 바뀌어야 한다.

## 6. 법률 규칙과 정답 후보

원자료의 상속순위·배우자·대습·재대습·상속분·연혁 구분을 유지하며 규칙표를 만든다. 각 규칙에 `규칙 ID / 쟁점 / 필요한 사실 / 적용·제외 조건 / 출처 / 경과규정 / 관련 시험 / 승인 상태`를 둔다.

공포일·시행일, 사망 시점·판례·부칙의 적용 관계를 구분한다. 몇 개 연도 구간만으로 모든 경과사건이 해결된다고 가정하지 않는다. 사망·결격·상속권 상실·포기를 같은 제외 상태로 합치지 않는다. 본위·대습·연속·배우자의 대습·재대습을 구분한다.

허용된 개발 환경에서 공식 법령·판례에 접근할 수 있으면 추가 대조하고, 그것이 원자료 밖의 확인임을 표시한다. 접근하지 못하면 검토 대기다. **초기 법률 승인 상태는 `PENDING`이며, 제품 기획 동의는 개별 규칙 승인이 아니다.**

### 6.1 산술 계약

- 정수 기반 정확한 기약분수를 사용하고 부동소수점 근삿값을 누적하지 않는다.
- 시작 지분 기본값은 1이며 1/3 등도 지원한다.
- 최초 피상속인의 지분 중 비율과 전체 물건에 대한 지분을 구분한다.
- 단계별 곱셈, 같은 최종 인물에게 귀속되는 유효 경로의 합산을 보존한다.
- 미확인 가지의 지분을 나머지 사람에게 재분배하거나 합계 1로 강제 정규화하지 않는다.
- 확인된 귀속 지분과 미해결 지분의 합이 시작 지분을 보존하는지 확인한다.
- 합계뿐 아니라 귀속자·규칙·중간 경로까지 정답 후보와 비교한다.

### 6.2 시험

계산 엔진 시험, 문서 추출 시험, 전체 사용자 흐름 시험을 분리한다. 정답 후보는 구현 결과를 보기 전에 사실관계·가정·근거·중간 지분·최종 지분·보류 여부를 기록한다.

배우자·자녀·직계존속·형제자매·방계혈족의 기본 사례, 시행 경계와 구법 조건, 선사망과 포기의 대비, 배우자가 남는 경우, 대습·재대습·연속상속, 다중 취득 경로, 시작 지분이 1이 아닌 경우를 포함한다.

누락자료·동명이인·날짜 불명확·미승인 규칙·미지원 과거 단계, 높은 OCR 점수에도 틀린 이름·날짜, 사용자 수정 후 재계산을 포함한다. 확실하지 않은 기대값을 숫자로 억지로 채우지 않는다.

보조 패키지가 있으면 기존 사례와 대조해 입력 모델에 맞는 시험 데이터를 설계한다. 산술 검산, 소프트웨어 테스트, 법률 승인, 업무 환경 검증은 별개 상태다. 구현 결과에 맞추어 정답 후보를 고치거나 같은 추정으로 코드·정답을 만들어 서로 맞는다는 이유로 검증 완료라고 하지 않는다.

## 7. PDF·OCR 후보와 검증 계획

### 7.1 후보

- PDF 입력·직접 추출·페이지 렌더링: PDF.js 우선 검토 [T1].
- 브라우저 OCR: Tesseract.js와 필요한 언어·문자 모델을 우선 검토 [T2–T4].
- 비교 후보: PaddleOCR.js / PaddleOCR의 브라우저 경로와 인식 모델 [T5–T6].

이는 채택 확정이 아니다. 공식 예제의 API·버전·모델 형식·라이선스와 실제 업무 성능을 따로 검증한다. 모든 후보를 최종 배포하라는 뜻이 아니다. OCR 엔진을 처음부터 새로 만들거나 학습하는 것은 기본 계획에서 제외한다.

Edge 확장 프로그램, ChatGPT 플러그인, MCP 서버를 업무 PC의 필수 요건으로 두지 않는다. 한국어 모델 존재만으로 한자 인명·세로쓰기·수기 제적등본까지 정확하다고 판단하지 않는다.

### 7.2 처리와 검토

직접 추출을 우선하되 페이지·영역 단위로 유효성을 판단한다. 제목만 텍스트이고 본문은 스캔인 경우, 깨진 텍스트층·부정확한 기존 OCR층을 처리하며 직접 추출과 OCR 결과의 중복을 막는다.

원문 확대·회전·영역 선택·재인식·수동 수정·인물 병합·분리를 계획한다. OCR 출력은 엔진과 무관한 텍스트·페이지·원문 좌표·인식 정보로 변환한다. 회전·크기 변경 뒤에도 좌표를 추적한다. 높은 인식 점수만으로 이름·일자·관계를 확정하지 않는다.

한글 인쇄체·숫자·한자 혼용·세로쓰기·저해상도·기울기·수기·훼손 표본을 분리한다. 원본을 변경하지 않고 전처리본을 만들며 인명·날짜를 그럴듯하게 자동 보정하지 않는다. 진행 표시·취소·실패 페이지 재시도·페이지 단위 메모리 관리를 설계한다. 특정 GPU를 전제하지 않는다.

### 7.3 오프라인·설치 계획

**이번에는 아래의 검증 방법을 설계하며 실제 설치·다운로드·실행은 하지 않는다.**

PDF·OCR 라이브러리, worker, WebAssembly/ONNX 실행 자원, 언어 모델, 필요한 문자·글꼴 자원을 로컬 배포본에 포함하는 방법을 정한다. 캐시 없는 첫 실행과 반복 실행에서 외부 다운로드·CDN·인증에 의존하지 않는지 시험한다.

`file://` 직접 실행을 실제 Edge에서 검증한다. 브라우저용이라는 이유만으로 파일 더블클릭 실행을 보장하지 않는다. 실행기·로컬 서버가 필요하면 대안·추가 배포물·정책 확인을 별도 의사결정으로 제시한다.

업무 PC에 Node.js·Python·개발 도구 설치를 요구하지 않는 구성을 우선하되 설치 전면 금지가 확정되었다고 쓰지 않는다. 허용된 로컬 서버는 동일 PC의 loopback 주소만 사용하고 외부 LAN에 기본 공개하지 않는다. 관리자 권한 임의 사용이나 Edge 보안 해제는 대안이 아니다.

이름·사망일·관계 필드 정확도, 수정 가능성, 시간·메모리·배포 용량을 측정할 계획을 세운다. 합격 기준·최대 입력 규모는 근거 있는 제안이며 소유자 확정 전에는 확정 요구가 아니다. 다른 브라우저 통과를 업무 Edge 통과로 보고하지 않는다.

## 8. 출력·저장

```text
[계산 상태와 전제]
최초 피상속인 / 시작 지분 / 기준일 / 확인된 전제 / 미확인 항목

[최종 귀속 후보와 지분]
인물 / 최소 식별정보 / 기약분수 / 미해결 여부

[단계별 계산]
상속 사건 / 규칙 / 본위·대습·연속 구분 / 계산 경로

[근거와 검토]
문서·페이지 / 법률 근거 / 제외 사유 / 검토 대기 / 프로그램·규칙 버전
```

결과만 복사와 과정까지 복사를 제공하되 잠정 결과의 핵심 경고를 제거하지 않는다. 출력은 장식보다 검토·복사를 우선한다.

사건 저장에는 구조화된 사실관계·확인 상태·출처 위치·계산 조건·스키마·규칙 버전을 포함하는 방안을 설계한다. 원본 PDF 포함과 암호화는 미정이며, PDF 미포함 시 원문 재연결·식별을 계획한다.

저장 입력을 검증하고 미지원 버전·훼손·과도한 크기·악성 문자열을 안전하게 다룬다. OCR 모델 캐시와 사건자료 저장을 구분한다. 자동 영구저장을 하지 않는다는 원칙을 명시적 저장 파일과 클립보드까지 자동 삭제한다는 약속으로 확대하지 않는다.

## 10. 저장소 저장·커밋

대상은 오직 `jhlee8403/inheritage`다. 이 전달문이 `main`의 초기 준비 문서로 먼저 커밋되어 있다면 그대로 읽고, 같은 내용으로 중복 커밋하지 않는다. 전달문 존재 여부와 실제 커밋을 확인하기 전부터 저장 완료로 보고하지 않는다.

1. 저장소 식별·원격·기본/현재 브랜치·변경 상태와 작업 규칙을 확인한다.
2. `docs/CODEX_HANDOFF.md`가 없고 첨부로만 제공되었다면 UTF-8로 보존한다. 기존 내용과 다르면 diff를 확인하고 갱신안 또는 별도 버전으로 처리한다.
3. 후속 작업은 정책에 맞는 문서 전용 브랜치에서 한다. 예: `docs/inheritance-design`. 이미 있으면 다른 사람의 작업을 덮어쓰지 않는다.
4. 전달문을 새로 저장할 필요가 있는 경우에만 별도 커밋한다. 권장 메시지: `docs: add inheritance Codex handoff`.
5. 설계 산출물은 별도 문서 커밋으로 기록한다. 권장 메시지: `docs: add inheritance design and validation plan`.
6. 경로를 지정해 스테이징하고 diff를 확인한다. 기존 staged 변경, 다른 사람의 수정, 원자료, 사건자료, 비밀값, 다운로드 모델, 빌드 산출물을 포함하지 않는다.
7. 허용된 인증·원격 쓰기 기능이 있으면 저장소 정책에 따라 작업 브랜치를 원격에 반영한다. 기본/보호 브랜치 무단 직접 push, 강제 push, 이력 재작성, 자동 merge를 하지 않는다.
8. 로컬 파일 작성·로컬 커밋·원격 push·PR 생성·기본 브랜치 반영을 구분한다. 가능한 경우 원격 반영을 실제로 다시 확인한다.
9. 권한·인증·기능이 부족하면 정확한 제한과 작성 파일을 보고한다. 토큰·비밀번호를 채팅으로 요구하거나 비공개 자격증명을 탐색하지 않는다.

이 지시는 전달문과 자체 작성 설계 문서 보존에 한정된다. 원본 U1·U2, 보조 기획 ZIP, 실제 사건자료 업로드 허가가 아니다.

2. 확인한 실행 환경·저장소, 권장 모델/강도와 실제 설정.
3. 작성·변경 문서와 주요 설계 결론.
4. 원자료·소유자 합의·새 제안·외부 확인·충돌.

9. 다음 단계의 소유자 결정과 그 결정 없이 설계 가능한 범위.
